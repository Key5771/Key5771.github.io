## Swift Concurrency에서 Sendable 이해하기

Swift Concurrency를 도입하면서 가장 자주 마주치게 되는 에러 메시지 중 하나는 다음과 같습니다.

>Type 'XXX' does not conform to the 'Sendable' protocol

기존에는 문제없이 사용되던 타입인데, 왜 갑자기 "Sendable" 오류가 발생하는걸까?

이 글에서는 Sendable 프로토콜이 왜 등장했는지, 그리고 Swift에서 Sendable이 무엇을 보장하려는 개념인지 기초부터 정리하고자 합니다.

-----

### 동시성에서 진짜 문제는 무엇인가

동시성의 가장 큰 위험은 데이터 경쟁(data race)입니다.

- 서로 다른 실행 컨텍스트(Task, 스레드, Actor)가 같은 메모리를 동시에 읽거나 수정하는 상황

이 문제는 런타임에서 발생하고, 재현이 어렵고, 디버깅도 매우 까다롭습니다.

Swift Concurrency의 목표는 명확합니다.

>"이런 문제를 런타임이 아니라 컴파일 타임에 막자"

Sendable은 이 목표를 달성하기 위한 핵심 도구입니다.

-----

### Sendable이란

`Sendable`은 다음을 의미하는 마커 프로토콜입니다.

>이 타입의 값은 서로 다른 동시성 실행 컨텍스트 사이에서 안전하게 전달될 수 있다.

```swift
protocol Sendable { }
```

즉, `Sendable`을 채택한 타입은 Task, actor, thread 경계를 넘어 이동해도 데이터 경쟁이 발생하지 않음을 보장해야 합니다.

-----

### 언제 Sendable이 필요할까

`Sendable`은 주로 다음 상황에서 요구됩니다.

1. Task 간 데이터 전달

```swift
Task {
    await process(data)
}
```

2. actor 외부 <-> actor 내부 데이터 전달

```swift
actor Store {
    func update(item: Item) { }
}
```

3. `@Sendable` 클로저

```swift
Task.detached {
    // 이 클로저는 @Sendable
}
```

이 경우, 전달되는 값들은 암묵적으로 `Sendable` 제약을 받습니다.

-----

### 어떤 타입이 Sendable한가

**값 타입(struct, enum)**

대부분의 값 타입은 자동으로 Sendable 합니다.

```swift
struct User {
    let id: Int
    let name: String
}
```

- 값 복사

- 공유 메모리 없음

즉, 데이터 경쟁 가능성이 없습니다.

**표준 라이브러리 타입**

Swift 표준 라이브러리의 많은 타입은 이미 `Sendable`을 채택하고 있습니다.

- Int, String, Bool

- Array<T>(T가 Sendable일 때)

- Dictionary<Key, Value>(Key, Value가 Sendable일 때)

-----

### Sendable이 아닌 타입

**참조 타입(class)**

클래스는 기본적으로 `Sendable`이 아닙니다.

```swift
final class User {
    var name: String
}
```

이유는 명확합니다.

- 참조 공유

- 동시에 접근하면 데이터 경쟁 가능

**mutable 상태를 가진 타입**

```swift
struct Counter {
    var value: Int
}
```

이 타입 자체는 struct지만, 여러 Task가 동시에 접근하면 안전하지 않을 수 있습니다.

그래서 Swift는 명시적인 `Sendable` 선언을 요구합니다.

-----

### Sendable 채택 방법

1. 컴파일러가 자동으로 판단하는 경우

```swift
struct User: Sendable {
    let id: Int
    let name: String
}
```

모든 프로퍼티가 Sendable이면 문제없이 컴파일됩니다.

2. 명시적인 Sendable 선언

```swift
struct Token: Sendable {
    let value: String
}
```

이 선언은 컴파일러에게 다음을 약속하는 것입니다.

>"이 타입은 어떤 동시성 컨텍스트에서도 안전하다"

3. `@unchecked Sendable`

```swift
final class Cache: @unchecked Sendable {
    private var storage: [String: Any] = [:]
}
```

이 키워드는 컴파일러의 검사를 우회합니다.

- 컴파일러 : "검사 안 할게"

- 개발자 : "안전성은 내가 책임질게"

⚠️ 매우 신중하게 사용해야 합니다.

-----

### @Sendable 클로저와 Sendable

`@Sendable` 클로저는 캡처하는 모든 값이 `Sendable`이어야 합니다.

```swift
let name = "Kim"

Task {
    print(name) // OK
}
```

```swift
class User {
    var name = "Kim"
}

let user = User()

Task {
    print(user.name)    // ❌ Sendable 아님
}
```

이 규칙 덕분에 Swift는 클로저 캡처로 인한 데이터 경쟁을 컴파일 타임에 차단합니다.

-----

### Sendable과 actor의 관계

actor 내부 상태는 암묵적으로 보호됩니다.

```swift
actor Store {
    var items: [String] = []
}
```

하지만 actor 외부로 값을 전달하는 순간 그 값은 `Sendable`이어야 합니다.

```swift
actor Store {
    func fetchItems() -> [String] {
        items
    }
}
```

- `[String]`은 `Sendable`

- 안전하게 전달 가능

-----

### Strict Concurrency와 Sendable

Swift 6의 Strict Concurrency 모드에서는:

- `Sendable` 위반 -> 경고가 아니라 에러

- 기존 코드도 수정 필요

이 변화는 불편함을 주지만, 동시에 코드의 동시성 안정성을 명확하게 만들어줍니다.

-----

### Sendable은 "옵션"이 아닙니다.

`Sendable`은 단순한 제약이 아닙니다.

- actor-isolated를 이해하게 하고

- nonisolated 사용을 조심하게 만들고

- async/await 설계를 더 명확하게 만들고

`Sendable`을 이해하면 Swift Concurrency의 설계 의도가 보이기 시작합니다.

-----

### 정리

- `Sendable`은 동시성 경계를 안전하게 넘을 수 있음을 보장하는 프로토콜

- 값 타입은 대부분 `Sendable`

- 참조 타입은 기본적으로 `Sendable` 아님

- `@unchecked Sendable`은 최후의 수단

- Swift는 `Sendable`을 통해 데이터 경쟁을 컴파일 타임에 차단

Swift Concurrency는 "개발자가 실수하지 않기를 바라는 모델"이 아니라 "실수할 수 없게 만드는 모델"입니다.

`Sendable`은 그 중심에 있는 개념입니다.
